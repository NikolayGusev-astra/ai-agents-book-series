# Момент, когда цепочка становится агентом

В прошлых частях порядок шагов диктовал разработчик: ретривер, потом модель, потом ответ. Агент начинается там, где этот порядок отдаётся модели: она сама решает, какой инструмент вызвать, и сама решает, когда остановиться.

Оркестрация переезжает с рук разработчика на модель. У разработчика остаются три вещи: схемы инструментов, состояние и точки контроля. Обе главы книги - про то, где проходят границы этого доверия.

# Один агент, четыре шага

Эволюция в главе 11 построена правильно: сначала механика руками, потом абстракция.

Один инструмент: ретривер по Wikivoyage, обёрнутый в @tool. Потом протокол вызова вручную - JSON-схема функции, bind_tools, рукописный узел исполнения. Руками видно тихую деталь, которую абстракция прячет: ToolMessage требует tool_call_id, а результат обязан вернуться в состояние, иначе цикл не замкнётся. Дальше граф: узел модели и узел инструментов, условное ребро - есть вызовы инструмента, идём в инструменты, нет - заканчиваем. Финал - рефакторинг на create_react_agent со счётчиком RemainingSteps.

Главный практический вывод главы: добавление второго инструмента не меняет граф. Меняется список TOOLS, и всё. Мультиагентность имеет смысл только после того, как одноагентная цепочка доказана - один инструмент, потом два.

В состоянии живёт редуктор: без него узлы возвращали бы полное состояние и размножали историю с каждым ходом.

# Шесть ошибок учебного кода, на которых книга ловит сама себя

Ценность этого раздела книги не в том, что автор ошибся, а в том, что каждая ошибка - типовая.

Алиасинг состояния: код присваивает список сообщений в локальную переменную и дописывает в него системный промпт - мимо редуктора. В трассе книги системное сообщение оказывается в конце истории и дублируется на каждой итерации.

Нет счётчика шагов в рукописном графе: несходящийся цикл крутится до лимитов API. Осторожность появляется только в разделе про RemainingSteps - то есть после того, как понадобилась.

"Чат-бот" без памяти: REPL-оболочка каждый раз вызывает модель со свежим состоянием. Это stateless single-turn агент, память появится только тремя главами позже.

Сырой возврат инструмента: в контекст модели уходит HTML Википутедии с тегами. Мусор стоит токенов, и модель не цитирует источники - ей не из чего.

Случайная погода: мок возвращает random, критерий "хорошей погоды" живёт в суждении модели, число итераций зависит от везения. Для воспроизводимого поведения нужен явный порог в коде.

Промпт как единственный рычаг: "не используй память модели" сделано текстом системного сообщения. Это мягкий контроль; жёсткие аналоги - принудительный вызов инструмента или маршрутизация с валидацией. Промпт - первый рычаг, не единственный.

Общее правило из всех шести: ограничения обязаны жить в коде - счётчик шагов, таймауты, пороги, подтверждение действий с побочными эффектами.

# Роутер против supervisor: обратный билет

Глава 12 надстраивает над одноагентным слоем два паттерна, и критерий выбора между ними один: возвращается ли управление координатору.

Роутер: вопрос классифицируется через структурированный вывод и уходит одному из двух агентов. Верхний уровень детерминирован, нижний остаётся гибким. Ограничение осознанное и названное: передача односторонняя. Вопрос "найди город с хорошей погодой и цену номера там" через роутер не проходит в принципе - он пересекает два домена.

Supervisor: агенты становятся инструментами супервизора. В трассе книги виден правильный порядок: transfer к агенту, внутри - его инструменты, transfer обратно, синтез у координатора. Именно возврат управления отличает supervisor от роутера - обратный билет против билета в одну сторону.

*"Заметки на полях". Наш аналог supervisor - канбан-оркестрация в Hermes, разбирали отдельно (ссылка следом). Профили под инженерные роли - scout, researcher, architect, executor, editor; каждая передача - карточка в базе задач, задача переживает перезапуск и возвращается на правку. Это supervisor-паттерн с внешней памятью: не состояние в общем словаре, а записи в базе. И это ровно ответ на главный риск, который глава не разбирает.*

Статья: [Шесть агентов вместо одного: собираем инженерную команду на Hermes](https://hermes-agent.ru/news/shest-agentov-vmesto-odnogo-sobiraem-inzhenernuyu/).

# Чего глава не разбирает, а стоило бы

Рекурсия: глубина вложенных вызовов растёт, и нужен предел итераций на уровне супервизора, а не только внутри каждого агента.

Общее состояние: одна схема на всех, история всех вызовов склеивается, контекст супервизора растёт линейно. В продакшене агентам нужны изолированные подграфы состояний, наружу - только итог.

Эскалация промпт-инъекций: данные из внешних API попадают в контекст супервизора и могут влиять на его план. В обратную сторону - инструкции супервизора видны агентам.

SQL-тулкит с записью: агенту бронирования отдаётся инструмент, умеющий писать в базу. Ограничение на чтение и подтверждение записи в примере не показаны.

Экономика: модель супервизора сильнее моделей агентов - это разумно по качеству декомпозиции и это главный рычаг стоимости всей системы. В книге одна строка.

*"Заметки на полях". Изоляцию контекстов мы выстрадали на гонках параллельных агентов: каждый ребёнок работает в собственном контексте, наружу отдаёт только итоговый самопроверенный результат, а слияние делает родитель. Память между репликами, которой нет у "чат-бота" из главы 11, у нас трёхслойная: сессия, память профиля, внешняя база знаний. Три наших разбора по ссылкам следом.*

# Что забрать в работу

1. Инструмент это контракт: имя, типы, докстринг, структурированный возврат. Модель выбирает инструмент по описанию - качество описания важнее качества реализации.
2. Ограничения в коде, не в промпте: счётчик шагов, таймауты, пороги, подтверждение действий с побочными эффектами.
3. Роутер для однозначной классификации, supervisor для запросов через домены. Критерий: возвращается ли управление координатору.
4. Мультиагентность только после доказанной одноагентной цепочки.
5. Состояние агентов изолировать, наружу отдавать только итог - иначе общий контекст растёт линейно с каждым вызовом.
