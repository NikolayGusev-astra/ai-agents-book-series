# Урок 6. Главы 11-12: агенты и мультиагентные системы

Источник: "AI Agents and Applications" (Manning, 2026), главы 11-12.
Формат: урок по /teachme, текст и схема.

# Одна мысль на весь урок

Цепочка из прошлых глав становится агентом, когда модель сама решает, какой инструмент вызвать и когда остановиться. Оркестрация переезжает с рук разработчика на модель, а у разработчика остаются три вещи: схемы инструментов, состояние и точки контроля. Обе главы - про то, где проходят границы этого доверия.

# Глава 11. Один агент, четыре шага

Эволюция построена правильно: сначала механика руками, потом абстракция.

1. Один инструмент: ретривер по Wikivoyage, обёрнутый в @tool.
2. Протокол вызова вручную: JSON-схема функции, bind_tools, рукописный узел исполнения. Руками видно тихую деталь: ToolMessage требует tool_call_id, а результат обязан вернуться в состояние - иначе цикл не замкнётся.
3. Граф: StateGraph, узлы llm_node и tools, условное ребро "есть вызовы инструмента - в tools, нет - в END".
4. REPL-оболочка. И рефакторинг на create_react_agent плюс RemainingSteps.

Главный практический вывод главы: добавление второго инструмента не меняет граф. Меняется список TOOLS - и всё.

В состоянии живёт редуктор Annotated[Sequence[BaseMessage], operator.add]: без него узлы возвращали бы полное состояние и размножали историю.

# Где книга сама себя ловит

Шесть мест, где учебный код книги демонстрирует ровно те ошибки, о которых предупреждает:

- Алиасинг состояния: присвоив state-словарь в локальную переменную и дописав в него сообщение, код мутирует список в обход редуктора. В трассе книги системное сообщение оказывается в конце истории и дублируется на каждой итерации.
- Нет счётчика шагов в рукописном графе: несходящийся цикл крутится до лимитов API. Осторожность появляется только в разделе про RemainingSteps - то есть после того, как понадобилась.
- "Чат-бот" без памяти: REPL каждый раз вызывает invoke со свежим состоянием. Это stateless single-turn агент, память появится только в главе 14.
- Сырой возврат инструмента: в ToolMessage уходит HTML Википутедии с тегами. Мусор в контексте, который стоит токенов. И модель не цитирует источники - ей не из чего.
- Случайная погода: мок возвращает random, критерий "nice weather" живёт в суждении модели, число итераций зависит от везения. Для воспроизводимости нужен явный порог в коде.
- Промпт как единственный рычаг: "не используй память модели" сделано SystemMessage. Это мягкий контроль; жёсткие аналоги - tool_choice="required" или маршрутизация с валидацией.

# Глава 12. Три агента: роутер и supervisor

Над одноагентным слоем строятся два паттерна.

Роутер: вопрос классифицируется через структурированный вывод и уходит одному из двух агентов, переход через Command(goto=...). Верхний уровень детерминирован, нижний остаётся гибким. Ограничение осознанное и названное: передача односторонняя, вопрос "найди город с хорошей погодой и цену номера там" через роутер не проходит в принципе.

Supervisor: агенты становятся инструментами супервизора (transfer_to_travel_info_agent). В трассе книги виден правильный порядок: transfer, внутри - инструменты агента, transfer обратно, синтез. Именно возврат управления отличает supervisor от роутера - "обратный билет" против "билета в одну сторону".

Риски, которые глава не разбирает:

- рекурсия: нужен предел итераций на уровне супервизора, а не только внутри ReAct-агента;
- общее состояние: operator.add склеивает историю всех вызовов, контекст растёт линейно; в проде агентам нужны изолированные подграфы состояний;
- эскалация промпт-инъекций: данные из внешних API попадают в контекст супервизора и могут влиять на его план;
- SQLDatabaseToolkit отдаёт модели запись в базу - для агента бронирования это осознанный риск без показанного ограничения на чтение;
- модель супервизора сильнее моделей агентов - это главный рычаг экономики системы, а в книге одна строка.

# Заметки на полях. Наше покрытие

Глава 11. Hermes - это и есть агент из главы 11 в продакшене: инструменты как скиллы, состояние как сессия, условное ребро как решение модели после каждого хода. Наша ловушка алиасинга состояния была своя: state вместо истории - то, о чём книга пишет одной строкой, у нас разобрано на живом замере. Статьи: [State и поиск на живом агенте](https://hermes-agent.ru/news/state-i-poisk-na-zhivom-agente/), [State вместо истории](https://hermes-agent.ru/news/state-vmesto-istorii-kak-malaya-model/).

Глава 12. Наш аналог супервизора - канбан-оркестрация в Hermes: шесть агентов вместо одного, профили под инженерные роли (scout, researcher, architect, executor, editor), каждая передача - карточка на канбане, задача переживает перезапуск и возвращается на правку. Это supervisor-паттерн с внешней памятью: не состояние в общем словаре, а записи в базе задач. Статья: [Шесть агентов вместо одного: собираем инженерную команду на Hermes](https://hermes-agent.ru/news/shest-agentov-vmesto-odnogo-sobiraem-inzhenernuyu/).

Разделение контекстов между агентами - наша боль из гонок параллельных детей: каждый агент в изолированном контексте, наружу - только итоговый самопроверенный результат. Это ровно рецепт "изолированные подграфы состояний" из списка рисков, только у нас он выстрадан. Статья: [Передача кода между LLM-агентами](https://hermes-agent.ru/news/peredacha-koda-mezhdu-llm-agentami-pochemu/).

Память между репликами, которой нет в "чат-боте" главы 11, у нас трёхслойная: сессия, память профиля, llm-wiki как внешняя база знаний. Статья: [Как устроена система памяти Hermes](https://hermes-agent.ru/news/hermes-agent-kak-ustroena-sistema-pamyati/).

# Что забрать в работу

1. Инструмент это контракт: имя, типы, докстринг, структурированный возврат. Модель выбирает инструмент по описанию - качество описания важнее качества реализации.
2. Ограничения в коде, не в промпте: счётчик шагов, таймауты, пороги, подтверждение действий с побочными эффектами. Промпт - первый рычаг, не единственный.
3. Роутер для однозначной классификации, supervisor для запросов через домены. Критерий выбора: возвращается ли управление координатору.
4. Мультиагентность только после доказанной одноагентной цепочки. Один инструмент, потом два, потом команда.
5. Состояние агентов изолировать, наружу отдавать только итог - иначе общий контекст растёт линейно с каждым вызовом.
