Два паттерна

Workflow: LLM выбирает один из заранее определённых переходов, сетка зашита в код. Агент: LLM выходит за пределы готового набора и сам определяет путь. Чем свободнее агент - тем дороже отладка.

Почему линейной цепочке становится тесно

Четыре сценария, где prompt | llm | parser ломается: ветвление по данным, повтор шагов по новой информации, явный контроль состояния, параллельные процессы. LangGraph закрывает их тремя механизмами: состояние, условное ветвление, циклы.

Три слова, на которых стоит весь LangGraph
State · Узлы · Рёбра 
# состояние: типизированный контракт между узлами
class ResearchState(TypedDict):
    user_question: str
    search_queries: Optional[List[SearchQuery]]
    search_results: Optional[List[SearchResult]]
    research_summary: Optional[str]

# узел: принимает состояние, возвращает ЧАСТИЧНОЕ обновление
def process_node(state: dict) -> dict:
    return {"output_data": do_something(state["input_data"])}

# условное ребро: роутер по состоянию выбирает следующий узел
def should_refine(state) -> str:
    if len(state["search_results"]) < 2:
        return "refine_queries"
    return "summarize_results"

Узел не подменяет состояние целиком - возвращает только изменённые поля, они мержатся. Роутер возвращает строку с именем следующего узла.

Research-агент из главы 4 становится графом

Шесть узлов вместо пяти шагов. Новый - Оценка релевантности: если качественных саммари меньше половины, поток возвращается на генерацию запросов. На цепочках такой цикл реализуется крайне неуклюже.

Лимит в три итерации: при исчерпании отчёт всё равно собирается из имеющегося. Деградация вместо отказа - инженерно зрелое решение.

Ловушка в коде самой книги
# так в книге - и это НЕ работает:
def route_based_on_relevance(state):
    state["iteration_count"] += 1   # мутация в роутере!
    if state["iteration_count"] >= 3:
        return "write_research_report"
    ...

Счётчик инкрементируется мутацией словаря прямо в условном ребре. Но книга же сама говорит: узлы возвращают частичное обновление, а не мутируют состояние. Если движок передаёт копию словаря - счётчик в графе не изменится, и защитный лимит не сработает: вечный цикл.

Правильно: счётчик живёт в состоянии и обновляется в узле, либо роутер возвращает пару (маршрут, обновление). Место, где граф обещает воспроизводимость, - именно там авторский код её ломает.
Что даёт переход на граф

Все шесть выигрышей из 5.5.4 растут из одного корня: явное состояние делает систему наблюдаемой. Прозрачная обработка, модульность, видимый порядок исполнения, локализация узкого места, точечные ошибки, дешёвое расширение.

И слабо раскрытый бонус: граф хранит историю исполнения. Инспекция траектории рассуждения, повтор из чекпоинта, ветвление от прежних решений. В линейной цепочке этого нет без ручной работы.

Критерий выбора

Переходить на граф стоит там, где линейной цепочке не хватает трёх вещей: явного состояния, ветвления по результату и цикла. Минимальный словарь невелик: TypedDict, StateGraph, add_node, add_edge, add_conditional_edges, set_entry_point, END, compile.
