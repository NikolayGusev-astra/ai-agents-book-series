# Зачем вообще MCP

К главе об агентах у нас агент с тремя инструментами. Каждый инструмент - функция рядом с агентом, в том же процессе, в той же виртуальной среде. Это работает, пока инструменты твои и их мало.

Теперь реальный корпус: агенту нужны погода, календарь, почта, тикет-трекер, вики, поиск по базе знаний. Каждая интеграция - свой код: аутентификация, лимиты, обработка ошибок, формат ответа, обновление при смене API провайдера. И главное: этот код пишут все, кому нужен тот же сервис. Десять команд, которым нужна погода, пишут десять одинаковых обёрток над одним API - и десять раз чинят их, когда провайдер меняет формат ответа.

Model Context Protocol (MCP) - открытый протокол, который меняет направление письма. Сервис сам публикует свои функции как MCP-сервер. Агент подключается как клиент и получает готовые инструменты. Обвязка написана один раз - тем, кто знает сервис лучше всех, - и её чинит тот же человек, который чинит сервис.

Протокол вышел в конце 2024 года и быстро стал стандартом де-факто: OpenAI и Google приняли его в API и SDK. Каталоги серверов: официальный портал Anthropic, mcp.so с шестнадцатью тысячами серверов, smithery.ai с пятью тысячами инструментов. Тысячи готовых интеграций, которые не пишут - подключают.

# Архитектура: хост, клиент, сервер

Три роли, и их стоит различать. MCP-хост - приложение агента: всё, что агент умеет и где живёт его состояние, внутри хоста. MCP-клиент - прослойка внутри хоста, держащая соединение с одним сервером; клиентов столько, сколько серверов. MCP-сервер - поставщик инструментов: публикует список функций (имя, описание, схему аргументов) и исполняет вызовы.

Ключевое свойство: для модели инструмент с MCP-сервера неотличим от локальной функции. Та же схема вызова, тот же выбор по описанию. Граф агента не меняется - меняется список инструментов, и в этом весь смысл: подключить новый сервер - это конфигурация, а не код.

Транспорт - два варианта, и выбор определяет профиль эксплуатации. stdio: сервер запускается хостом как дочерний процесс на той же машине, обмен через стандартные ввод-вывод, ноль сети и аутентификации - для локальных ресурсов и быстрого старта. Streamable HTTP: сервер как сетевой сервис для прода и общих источников. В проде требует нормальной аутентификации - книга упоминает это одной строкой, а сервер без аутентификации в интернете это дыра.

Ошибка интеграции номер один: сетевой инструмент асинхронен. Локальная функция отвечает за микросекунды, MCP-сервер через сеть - за сотни миллисекунд и дольше. Весь путь исполнения становится async, и забытый await - самый частый способ уронить интеграцию.

# Как устроен сервер изнутри

Минимальный сервер на FastMCP 2 - основном Python SDK:

```python
from fastmcp import FastMCP

mcp = FastMCP("mcp-accuweather")

@mcp.tool(description="Get weather conditions for a location.")
async def get_weather_conditions(location: str) -> Dict:
    # поиск location_key, потом текущие условия
    ...

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="127.0.0.1",
            port=8020, path="/accu-mcp-server")
```

Вся публикация - декоратор @mcp.tool с описанием. Описание делает ту же работу, что и у локального инструмента: по нему модель решает, звать ли его. Сервер запускается одной командой и висит на порту как обычный HTTP-сервис. Официальные SDK есть для Python, JavaScript, Java, Kotlin, C# - протокол с нуля писать не нужно, повторишь то, что уже решено.

# Проверка до интеграции: MCP Inspector

Самый полезный инструмент главы - MCP Inspector. Визуальная консоль: подключаешься к серверу, видишь список инструментов глазами потребителя, вызываешь руками, смотришь сырой ответ.

Порядок проверки книга проводит правильно: сервер - инспектор - тестовый клиент кодом - и только потом агент. Если инструмент сломан, ты видишь это в инспекторе напрямую: статус, сырой JSON, схему. Если проверять сразу агентом, поломка доедет замаскированной: агент отвечает странно, и ты отлаживаешь агента, хотя сломан сервер.

Дополнение из практики: инспектор - это ещё и проверка описания глазами потребителя. Формулировка, ясная автору сервера, в инспекторе часто читается иначе - и это последний шанс поправить её до того, как её увидят тысячи агентов.

# Память: чекпоинты вместо списка сообщений

Наивное решение памяти - хранить и пересылать историю сообщений - несёт только текст. Теряются результаты инструментов, промежуточные переменные, метаданные исполнения.

LangGraph решает это чекпоинтами: снимок полного состояния графа после каждого узла. Один механизм закрывает три сценария. Многоходовой диалог: "а в том же городе?" разрешается, потому что поднято состояние прошлого хода. Восстановление после сбоя: продолжение с последнего снимка без повторного исполнения дорогих шагов. Human-in-the-loop: остановка на снимке для согласования с человеком и продолжение ровно с места остановки.

Механика: checkpointer снимает состояние, thread_id связывает снимки с сессией. Пользователь может иметь несколько тредов; передал старый thread_id - граф поднял последний снимок. Вручную это воспроизводится явно: получить историю снимков, взять нужный, перемотать граф вызовом с пустым входом и конфигурацией снимка. Это же открывает ветвление: из любого снимка строится альтернативная ветка диалога.

Хранилище по стадиям зрелости: InMemorySaver - разработка, SqliteSaver - локальная персистентность, PostgresSaver - прод с конкурентным доступом.

# Ловушка Responses API

Связка модели с памятью требует двух флагов одновременно: use_responses_api=True и use_previous_response_id=True. Второй без первого - несовместимость. Первый без второго - тонкий провал: LangChain пересылает полную историю, а Responses API считает это повторной подачей и возвращает ошибку. Второй флаг - условие корректности, а не оптимизация.

И побочный эффект, который книга упоминает вежливо: при отправке только идентификатора предыдущего ответа сырой контекст диалога хранится у OpenAI, а не в твоём процессе. Токены экономятся - а состояние уехало внешнему провайдеру. Для корпоративного контура это вопрос политики данных, а не деталь настройки.

# Заметки на полях. Наш живой стек

У нас в конфиге Hermes десять MCP-серверов, и они показывают оба транспорта в продакшене. По stdio - локальные процессы: наш RAG-шлюз, три интеграции Astra (Jira, Confluence, Bitbucket Data Center), почта и календарь RuPost. По HTTP - сетевые сервисы: документация библиотек, онтологии, корпоративный поиск. Восемь разных систем - ноль обвязок в нашем коде: каждая подключена конфигурацией в несколько строк. Когда поставщик обновляет свой MCP-сервер, мы обновляем бинарник - код агента не меняется. Это и есть ответ на вопрос "зачем", показанный на работающем примере.

Чему научила эксплуатация, чего нет в книге. Первое: write-path валидация. Читать из MCP-сервера безопасно, писать - значит менять живую систему: создать тикет, откомментировать в Confluence, отправить письмо. Каждую запись агент должен проверять контрактом - что пишем, куда, кто подтвердил, - иначе один неверно понятый запрос превращается в случайный тикет в чужой очереди. Второе: MCP-стек сам живая система. Серверы обновляются, ломаются, меняют схемы - мы сверяем версии и прод-статус еженедельно.

Память у нас разъехалась на три слоя, что совпадает с книжным делением: сессия - краткосрочная (thread_id из книги), память профиля - долгосрочная пользовательская, база знаний - долгосрочная общая. Важное отличие: долгосрочная память ищется, а не поднимается целиком. Она не жмётся в контекст, и попытка протащить её через промпт - путь к затоплению контекста.

# Что забрать в работу

1. MCP - разворот ответственности: обвязка живёт у поставщика. Не пиши свою, если есть сервер; публикуй свою, если твой сервис нужен другим.
2. Сетевой инструмент асинхронен - весь путь исполнения. Забытый await - главная ошибка интеграции.
3. Сервер проверяй в инспекторе до агента: сырой ответ и схему глазами потребителя.
4. Описание MCP-инструмента читает модель. Слабое описание - и инструмент не используется.
5. Чекпоинты - один механизм на три сценария. thread_id - ключ. Хранилище по зрелости: память - SQLite - PostgreSQL.
6. use_previous_response_id - условие корректности. И решай осознанно, чьё теперь состояние.
