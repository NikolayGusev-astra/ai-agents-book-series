# Зачем вообще MCP

К главе 11 у нас есть агент с тремя инструментами. Каждый инструмент - функция рядом с агентом, в том же процессе, с той же виртуальной средой. Это работает, пока инструменты твои и их мало.

Теперь реальный корпус: агенту нужны погода, календарь, почта, тикет-трекер, вики, поиск по базе знаний, конвертер документов. Каждая интеграция - это свой код: аутентификация, лимиты, обработка ошибок, формат ответа, обновление при смене API провайдера. И главное: этот код пишут все, кому нужен тот же сервис. Десять команд, которым нужна погода, пишут десять одинаковых обёрток над одним и тем же API - и десять раз чинят их, когда провайдер меняет формат ответа.

Model Context Protocol (MCP) - открытый протокол от Anthropic (конец 2024, быстро ставший стандартом де-факто: OpenAI и Google приняли его в API и SDK), который меняет направление письма. Сервис сам публикует свои функции как MCP-сервер. Агент подключается как клиент и получает готовые инструменты. Обвязка написана один раз - тем, кто знает сервис лучше всех, - и её чинит тот же человек, который чинит сервис.

Книга приводит таблицу каталогов: официальный портал Anthropic, mcp.so с более чем 16 000 серверов, smithery.ai с пятью тысячами инструментов. Тысячи готовых интеграций, которые не нужно писать - только подключить.

# Архитектура: хост, клиент, сервер

Три роли, и их стоит различать:

- MCP-хост - приложение агента. Всё, что агент умеет и где живёт его состояние, - внутри хоста.
- MCP-клиент - прослойка внутри хоста, держащая соединение с одним сервером. Клиентов столько, сколько серверов.
- MCP-сервер - поставщик инструментов. Публикует список функций: имя, описание, схему аргументов. Исполняет вызовы.

Ключевое свойство: для модели инструмент с MCP-сервера неотличим от локальной функции. Та же схема вызова, тот же механизм выбора по описанию, что мы разобрали в главе 11. Граф агента не меняется - меняется только список TOOLS, и в этом весь смысл: подключение нового сервера - это конфигурация, а не код.

# Транспорт: где физически живёт сервер

Два варианта, и выбор определяет профиль эксплуатации:

stdio - сервер запускается хостом как дочерний процесс на той же машине. Обмен - через стандартные ввод-вывод. Ноль сети, ноль аутентификации (процесс твой), самый быстрый старт. Подходит для локальных ресурсов: файлы, локальные базы, инструменты на твоём железе.

Streamable HTTP - сервер как сетевой сервис. Умеет отвечать нескольким клиентам, живёт отдельно от агента, обновляется независимо. Это вариант для прода и для общих источников данных. В проде требует нормальной аутентификации - книга упоминает это одной строкой, а зря: неоткрытый наружу сервер с нулевой аутентификацией в закрытом контуре терпимо, тот же сервер в интернете - дыра.

Ошибка интеграции номер один, по опыту книги и нашему: сетевой инструмент асинхронен. Локальная функция отвечает за микросекунды, MCP-сервер через сеть - за сотни миллисекунд и дольше. Весь путь исполнения становится async, и забытый await в цепочке - самый частый способ уронить интеграцию.

# Как устроен сервер изнутри

Минимальный сервер на FastMCP 2 - основной Python SDK книги:

```python
from fastmcp import FastMCP

mcp = FastMCP("mcp-accuweather")

@mcp.tool(description="Get weather conditions for a location.")
async def get_weather_conditions(location: str) -> Dict:
    # поиск location_key в AccuWeather, потом текущие условия
    ...

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="127.0.0.1",
            port=8020, path="/accu-mcp-server")
```

Вся публикация - декоратор @mcp.tool с описанием. Описание здесь делает ту же работу, что и в главе 11: по нему модель решает, звать ли инструмент. Сервер запускается одной командой и висит на порту как обычный HTTP-сервис.

SDK не обязательно брать именно этот - официальные есть для Python, JavaScript, Java, Kotlin, C#. Писать протокол с нуля книга справедливо не рекомендует: повторишь то, что уже решено в SDK.

# Проверка до интеграции: MCP Inspector

Самый полезный инструмент главы - MCP Inspector (npx @modelcontextprotocol/inspector). Это визуальная консоль: подключаешься к серверу, видишь список инструментов глазами потребителя, вызываешь руками, смотришь сырой ответ.

Порядок проверки, который книга проводит правильно: сервер - инспектор - тестовый клиент кодом - и только потом агент. Если инструмент сломан, ты видишь это в инспекторе напрямую: статус, сырой JSON, схему. Если проверять сразу агентом, поломка доедет до тебя замаскированной: агент отвечает странно, и ты отлаживаешь агента, хотя сломан сервер.

Наше дополнение из практики: инспектор - это ещё и проверка схемы глазами потребителя. Описание инструмента, которое казалось автору сервера ясным, в инспекторе часто читается иначе - и это последний шанс поправить формулировку до того, как её увидят тысячи агентов.

# Память: чекпоинты вместо списка сообщений

Вторая половина главы - про память. Из главы 11 помним "чат-бота", который не помнит. Наивное решение - хранить и пересылать историю сообщений - работает, но несёт только текст: теряются результаты инструментов, промежуточные переменные, метаданные исполнения.

LangGraph решает это чекпоинтами: снимок полного состояния графа после каждого узла (супер-шага). Один механизм закрывает три сценария:

- многоходовой диалог: "а в том же городе?" разрешается, потому что поднято состояние прошлого хода;
- восстановление после сбоя: продолжение с последнего снимка без повторного исполнения дорогих шагов;
- human-in-the-loop: остановка на снимке для согласования с человеком и продолжение ровно с места остановки.

Механика: checkpointer - компонент, снимающий состояние; thread_id - идентификатор сессии, связывающий снимки с диалогом. Пользователь может иметь несколько тредов. Передал старый thread_id - граф поднял последний снимок. Причём вручную это воспроизводится явно: get_state_history отдаёт список снимков, get_state возвращает состояние на выбранном, invoke(None, config) перематывает на него. Это же открывает ветвление: из любого снимка можно построить альтернативную ветку диалога.

Хранилище по стадиям зрелости: InMemorySaver - разработка и тесты, SqliteSaver - локальная персистентность, PostgresSaver - прод (конкурентный доступ, надёжность).

# Ловушка Responses API

Связка модели с памятью требует двух флагов одновременно: use_responses_api=True и use_previous_response_id=True. Второй без первого - несовместимость. Первый без второго - тонкий провал: LangChain пересылает полную историю, а Responses API считает это повторной подачей и возвращает ошибку. Второй флаг - условие корректности, а не оптимизация.

И побочный эффект, который книга упоминает вежливо: при отправке только идентификатора предыдущего ответа сырой контекст диалога хранится у OpenAI, а не в твоём процессе. Токены экономятся - а состояние уехало внешнему провайдеру. Для корпоративного контура это вопрос политики данных, а не деталь настройки.

# Заметки на полях. Наш живой стек

У нас в конфиге агента десять MCP-серверов, и они показывают оба транспорта в продакшене:

- stdio (локальные процессы): наш RAG-шлюз; тикет-трекер, корпоративная вики и репозитории кода; почта и календарь.
- HTTP (сетевые сервисы): документация библиотек, онтологии, корпоративный поиск.

Это и есть ответ на вопрос "зачем": RAG, тикеты, вики, почта, календарь, онтологии - восемь разных систем, ноль обвязок в нашем коде. Каждая подключена конфигурацией в несколько строк. Когда поставщик обновляет свой сервер, мы обновляем клиент - код агента не меняется.

Чему нас научила эксплуатация, чего нет в книге:

- write-path валидация. Читать из MCP-сервера безопасно. Писать - значит менять живую систему: создать тикет в трекере, оставить комментарий в вики, отправить письмо. Каждую запись агент должен проверять контрактом (что именно пишем, куда, кто подтвердил), иначе один неверно понятый запрос превращается в случайный тикет в чужой очереди.
- MCP-стек - сам живая система. Серверы обновляются, ломаются, меняют схемы. Мы сверяем версии и прод-статус стека еженедельно - книга об эксплуатационной стороне не говорит ничего.
- Чекпоинты у нас разъехались на три слоя: сессия (краткосрочная, как thread_id в книге), память профиля (долгосрочная пользовательская), llm-wiki (долгосрочная общая). Важно, что долгосрочная память ищется, а не поднимается целиком: она не жмётся в контекст, и попытка протащить её через промпт - путь к затоплению контекста, о котором мы писали отдельно.

# Что забрать в работу

1. MCP - разворот ответственности: обвязка живёт у поставщика. Не пиши свою, если есть сервер; публикуй свою, если твой сервис нужен другим.
2. Сетевой инструмент асинхронен - весь путь исполнения. Забытый await - главная ошибка интеграции.
3. Сервер проверяй в инспекторе до агента: сырой ответ и схему глазами потребителя.
4. Описание MCP-инструмента читает модель - как и у локального @tool. Слабое описание - и инструмент не используется.
5. Чекпоинты - один механизм на три сценария. thread_id - ключ. Хранилище по зрелости: память - SQLite - PostgreSQL.
6. use_previous_response_id - условие корректности. И решай осознанно, чьё теперь состояние.
