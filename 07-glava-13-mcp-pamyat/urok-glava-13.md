# Урок 7. Глава 13: MCP и память агентов на чекпоинтах

Источник: "AI Agents and Applications" (Manning, 2026), глава 13 (MCP-серверы) и 14 (память, гардрейлы - следующий урок).
Формат: урок по /teachme, текст и схема.

# Одна мысль на весь урок

Агент из прошлых глав умеет вызывать инструменты, но каждый инструмент - это обвязка, которую пишет потребитель. Глава 13 переворачивает это: обвязку пишет поставщик. А чтобы агент помнил диалог между ходами, нужен не список сообщений, а снимки состояния - чекпоинты.

# Проблема, которую решает MCP

Вспомни агент из главы 11: три инструмента, каждый - функция с описанием. Для одного агента в одном процессе это нормально. А теперь представь двадцать агентов у десяти команд, и каждому нужен погодный сервис. Без протокола каждая команда пишет свою обвязку: аутентификацию, лимиты, обработку ошибок, формат - двадцать раз один и тот же код.

Model Context Protocol (MCP) - открытый протокол, который решает это разворотом ответственности: погодный сервис сам публикует свои функции как MCP-сервер, а любой агент подключается к нему как клиент. Обвязку пишет тот, кто знает сервис лучше всех, - один раз.

Три роли в архитектуре:

- хост - приложение агента (то, что у нас Hermes);
- клиент - прослойка внутри хоста, которая держит соединение с одним сервером;
- сервер - поставщик инструментов: публикует список функций с описаниями и исполняет вызовы.

Для агента инструмент из MCP-сервера неотличим от локальной функции: та же схема "имя + описание + аргументы". Разница под капотом: путь исполнения становится асинхронным (сервер может жить в другом процессе или на другой машине), и это самая частая точка интеграции, о которую спотыкаются.

Транспорта два: stdio - сервер запускается как дочерний процесс на той же машине (локальные инструменты, ноль сети), и Streamable HTTP - сервер как сетевой сервис (прод, общие источники данных).

# Практикум: погодный сервер

Книга проходит полный цикл: сервер на AccuWeather API - проверка без клиентского кода через MCP Inspector (визуальная отладка: видишь список инструментов глазами потребителя и вызываешь их руками) - тестовый хост кодом - подключение к агенту.

Важен порядок: сервер проверяется до встраивания в агента. Если что-то не так, ты видишь это в инспекторе напрямую, а не через непонятное поведение агента.

# Память: почему список сообщений не решение

Из главы 11 мы помним "чат-бот", который не помнит. Наивное решение - хранить историю переписки и передавать её целиком - работает, но теряет всё, кроме текста: результаты инструментов, промежуточные переменные, метаданные.

LangGraph предлагает чекпоинты: снимок полного состояния графа после каждого узла. Один механизм закрывает три сценария сразу:

1. многоходовой диалог: "а в том же городе?" разрешается, потому что состояние прошлого хода поднято;
2. восстановление после сбоя: продолжение с последнего снимка без повторного исполнения дорогих шагов;
3. human-in-the-loop: остановка на снимке для согласования с человеком и продолжение ровно с того места.

Два ключевых понятия: checkpointer - компонент, который снимает состояние; thread_id - идентификатор сессии, который связывает снимки с диалогом. Передал thread_id в новый вызов - граф поднял последний снимок и продолжил.

Хранилище по стадиям: InMemorySaver для разработки, SQLite для локальной персистентности, PostgreSQL для прода (конкурентный доступ, надёжность).

# Ловушка, которую книга прячет в скобках

Связка модели с памятью через OpenAI Responses API требует двух флагов: use_responses_api=True и use_previous_response_id=True. Второй без первого - ошибка; первый без второго - тонкий провал: LangChain шлёт полную историю каждый раз, а Responses API считает это повторной подачей и падает. То есть второй флаг - не оптимизация, а условие корректности.

Побочный эффект: сырой контекст диалога теперь живёт на стороне OpenAI, а не у тебя в процессе. Экономия токенов - да, но состояние ушло внешнему провайдеру, и это надо учитывать в политиках по данным.

# Заметки на полях. Наше покрытие

Чекпоинты. Снимок полного состояния против списка сообщений - у нас это развели на два уровня: state как сессия плюс внешняя память профиля и llm-wiki. Разбор: [state и поиск на живом агенте](https://hermes-agent.ru/news/state-i-poisk-na-zhivom-agente/). Трёхслойная память (сессия, профиль, база знаний) соответствует делению книги на краткосрочную и долгосрочную, но долгосрочную мы вынесли из контекста модели - она не жмётся в промпт, она ищется. Статья: [как устроена система памяти Hermes](https://hermes-agent.ru/news/hermes-agent-kak-ustroena-sistema-pamyati/). Крайняя форма персистентности - memvid: вся память в одном файле: [memvid](https://hermes-agent.ru/news/memvid-pamyat-dlya-ai-agentov-v/).

MCP. Наш стек построен на MCP: Mattermost, Confluence, OntoNet, shturman-core - всё подключено как MCP-серверы к Hermes-хосту. Урок эксплуатации, который книга не даёт: write-path валидация. Читать из MCP-сервера безопасно, писать - это изменения в живой системе (Jira-тикет, комментарий в Confluence), и каждую запись надо проверять контрактом, иначе агент с правами на запись становится источником случайных изменений. Плюс gард-правило: MCP-стек - живая система со своими версиями и деградациями, и его надо периодически сверять (у нас это еженедельная сверка версий и прод-статуса).

# Что забрать в работу

1. MCP - разворот ответственности: обвязку пишет поставщик, один раз. Не дублируй её у себя.
2. Инструмент из сети = асинхронность под капотом. Забыть await - самая частая ошибка интеграции.
3. Сервер проверяй в инспекторе до встраивания в агента.
4. Чекпоинты - один механизм на три сценария: диалог, восстановление, human-in-the-loop. thread_id - ключ ко всем трём.
5. use_previous_response_id - условие корректности, не оптимизация. И знай, чьё это состояние теперь.
